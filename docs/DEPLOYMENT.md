# Deploying CodeArena (Java)

Frontend on Vercel, backend + compiler service on Render, database on MongoDB Atlas.
`render.yaml` and `frontend/vercel.json` do most of the configuration for you - this
doc covers the parts only you can do (creating accounts, connecting the repo, and
filling in secrets), roughly in the order you'll hit them.

## 1. MongoDB Atlas

1. Create a free account at [mongodb.com/cloud/atlas](https://www.mongodb.com/cloud/atlas) and a new **M0 (free)** cluster.
2. **Database Access** → add a new database user (username/password, "Read and write to any database" is fine for this project).
3. **Network Access** → add `0.0.0.0/0` (allow access from anywhere). Render's outbound IPs aren't static on the free plan, so this is the practical option; it's still gated by the username/password.
4. **Connect** → "Drivers" → copy the connection string. It looks like:
   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority
   ```
   Add a database name before the `?`, e.g. `.../codearena?retryWrites=...`. This full string is your `MONGODB_URI`.

## 2. Render (backend + compiler service)

1. Push this repo to GitHub (already done if you're reading this from the repo).
2. In the Render dashboard: **New** → **Blueprint**, connect the GitHub repo. Render reads `render.yaml` at the repo root and proposes both services (`code-arena-backend`, `code-arena-compiler`).
3. Before the first deploy, Render will prompt for the env vars marked `sync: false` in `render.yaml`:
   - `MONGODB_URI` on the backend service - the Atlas connection string from step 1.
   - `CORS_ALLOWED_ORIGINS` on the backend service - leave a placeholder for now (e.g. `http://localhost:5173`); you'll update it once the Vercel URL exists (step 3 below).
   - `GEMINI_API_KEY` on the backend service - optional; only needed for the AI features.
   - `JWT_SECRET` is auto-generated by Render (`generateValue: true`) - nothing to do here.
4. Deploy. Each service exposes `GET /actuator/health` for Render's health check - watch the deploy logs if a service doesn't go live.
5. `COMPILER_URL` defaults to `https://code-arena-compiler.onrender.com` in `render.yaml`, matching the service name Render will assign it. If you rename the compiler service, update `COMPILER_URL` on the backend to match.
6. Once live, note the backend's URL (e.g. `https://code-arena-backend.onrender.com`) - the frontend needs it next.

Render's free plan spins services down after 15 minutes of inactivity; the first request after that takes a while (cold start) as both services wake back up.

## 3. Vercel (frontend)

1. In the Vercel dashboard: **Add New** → **Project**, import the same GitHub repo.
2. Set **Root Directory** to `frontend` (this repo is a monorepo - Vercel needs to know where the frontend actually lives). Vercel auto-detects the Vite framework preset; `frontend/vercel.json` adds the SPA rewrite so client-side routes like `/problems/123` don't 404 on a direct load.
3. Add an environment variable: `VITE_BACKEND_URL` = the Render backend URL from step 2.6 (e.g. `https://code-arena-backend.onrender.com`). Vite bakes this in at build time, so it must be set before deploying.
4. Deploy. Note the resulting Vercel URL (e.g. `https://code-arena-java.vercel.app`).

## 4. Close the loop: update CORS

Back in Render, set the backend's `CORS_ALLOWED_ORIGINS` to the real Vercel URL from step 3.4, then redeploy the backend. Until this matches, the browser will block the frontend's requests to the API.

## Verifying it worked

- `https://<backend>.onrender.com/actuator/health` and `https://<compiler>.onrender.com/actuator/health` both return `{"status":"UP"}`.
- The Vercel URL loads, and signing up / logging in works (exercises the whole chain: Vercel → Render backend → Atlas, plus the JWT flow).
- Submitting a solution to a problem works (exercises Render backend → Render compiler service).
